# P3 知识库泄漏审计报告（严格口径 0.5）

- 日期：2026-11-23（严格口径复核）
- 脚本：`knowledge/audit_leakage.py`
- 数据：知识库 `knowledge.jsonl`（52.5 MB / 7,578 行）、测试集 `cache/dataset/test.jsonl`（300 行 / 150 对）
- 结果：`cache/knowledge/audit/leakage-audit.json` 与 `leakage-audit.md`；
  最终索引卡片复核为 `leakage-audit-cards.json` 与 `leakage-audit-cards.md`（本地缓存，不入库）
- 审计耗时：知识库 16.91 s，最终卡片 10.74 s

## 1. 为什么从严

作业要求测试集不得进入知识库。只做 idx / commit / 哈希比对只能排除“同一条记录”，
排不掉同一函数在不同提交、不同分支、不同代码切分下的内容近似；而这类近似一旦被
检索命中，模型会直接看到测试样本的函数主体或修复说明。按最严格的合规口径，
**任何内容层面的近似都按污染处理**，因此在旧口径（包含度 ≥0.8）之外：

1. 阈值从 0.8 收紧到 **0.5**；
2. 不再只保留每个测试样本的最佳匹配，而是枚举**所有** ≥0.5 的配对；
3. 测试函数注释里出现的 CVE 编号，若知识库有同编号记录，也一并剔除；
4. 剔除后重建卡片与 BM25，再对**索引卡片**做一次残余审计，直到残余为 0。

## 2. 审计口径

1. **idx**：直接比较两边的 `idx` 整数值。
2. **commit**：从 `commit_url` 提取 `/commit/<hash>`；知识库无 URL 时退回 `commit_id`。
3. **CVE（直接）**：`test.jsonl` 没有 `cve` 字段，无法按编号直接比对。
4. **CVE（文本提及）**：扫描测试函数中的 `CVE-\d{4}-\d{4,7}`，与知识库 `cve` 比较；
   命中即按严格口径剔除对应知识记录。
5. **规范化哈希**：去掉注释与所有非字母数字字符、转小写后取 SHA-1，比较是否全等。
6. **近似片段**：规范化后取 8 字符滑窗，按“交集 / 较短一方片段数”计算包含度。
   同一条函数计算两种文本形态并取最大值：
   - `full`：完整函数规范化后截断 4,000 字符；
   - `raw4000`：先截断原始函数 4,000 字符再规范化（与索引卡片的 `func_excerpt` 一致）。

   加 `raw4000` 是因为长函数在卡片截断后的规范化长度会变小、包含度会略升；
   只算 `full` 会出现“知识库审计通过、建完索引又冒出 0.5 以上残余”的循环。
   两种形态取最大，保证审计结论对知识库原文和索引卡片同时成立。

限制：包含度是词面近似，不是语义等价；截断 4,000 字符会漏掉超长函数尾部的差异。

## 6. 处置与最终库规模

1. `knowledge/audit_leakage.py` 默认阈值改为 `0.5`，输出顶层 `excluded_knowledge_idxs`。
2. `rag/build_index.py` 读取该清单，并合并最终卡片残余审计的剔除项：
   - 原始 7,578 行 → 7,574 条唯一卡片（重复 4 条保留首条，坏行 0）；
   - 剔除 **77** 条（近似重复 75 + CVE 文本提及 2）；
   - **最终 7,497 条入索引**，`manifest.json` 记录 `threshold_containment = 0.5`。
3. 剔除后重新生成 `cards.jsonl` 与 `bm25.json`，再跑一次卡片残余审计：
   - 残余配对 **0**，最高包含度 **0.4941**（低于阈值）；
   - CVE 文本提及交集 **0**。
4. 如需保留全部知识做研究，可用 `python -m rag.build_index --include-leaky`；
   评测与演示环境不要使用。

## 7. 残余风险

1. **词面近似不是语义等价**：改标识符、重排代码、换写法的同一漏洞可能低于 0.5，
   无法被 8-gram 包含度发现。
2. **4,000 字符截断**：超长函数只比较前 4,000 个规范化字符，尾部差异不计入。
3. **同项目同类型的提示风险**：低于 0.5 的同项目记录仍可能通过 `cve_desc` 或
   提交标题给出漏洞方向；全部剔除会显著削弱知识库，本次未做。
4. **CVE 直接比对不可用**：测试集没有 `cve` 字段，只能靠函数文本提及，覆盖不完整。
5. **索引产物是本地缓存**：`cache/` 不入库；换机器后必须重新跑审计与建索引，
   否则可能拿到未剔除的旧索引。

## 8. 对检索自测的影响

用收紧前同一批 40 个案例（`cache/knowledge/selftest/cases-before.json`）复测：

| 指标 | 收紧前（7,560 条，0.8） | 收紧后（7,497 条，0.5） |
|---|---|---|
| CVE 描述 query：top-3 命中同一 CVE | 40/40 = 100% | 40/40 = 100% |
| CVE 描述 query：top-3 命中同一记录 | 39/40 = 97.5% | 39/40 = 97.5% |
| 同项目不同 CVE 负例：误命中 | 1/39 = 2.6% | 1/39 = 2.6% |
| 修复提交标题 query：top-3 命中同一 CVE | 33/34 = 97.1% | 33/34 = 97.1% |
| 函数签名 query：top-3 命中同一 CVE | 38/40 = 95.0% | 38/40 = 95.0% |
| 单次检索中位数 / P95 | 23.15 ms / 53.30 ms | 19.69 ms / 40.92 ms |

- 40 个案例没有任何一个因剔除而消失（`cases_missing_from_index = []`），因此没有
  “查询命中不到”的情况；命中率没有为好看而调参。
- 正例 100% 仍是**自检索上界**（query 来自卡片自身的 NVD 描述），不代表泛化能力；
  有信息量的是负例误命中与签名/标题探针。

## 9. 复现

```powershell
$env:FUNCGUARD_KNOWLEDGE_PATH = "<knowledge.jsonl 路径>"

# 1) 知识库审计（严格 0.5，全量配对 + CVE 文本提及）
python -m knowledge.audit_leakage --knowledge $env:FUNCGUARD_KNOWLEDGE_PATH --threshold 0.5

# 2) 重建卡片与 BM25（自动读取剔除清单）
python -m rag.build_index --knowledge $env:FUNCGUARD_KNOWLEDGE_PATH

# 3) 最终卡片残余审计（应为 0 对）
python -m knowledge.audit_leakage --cards --threshold 0.5

# 4) 固定案例复测（收紧前后同一批 query）
python -m rag.selftest --cases-file cache\knowledge\selftest\cases-before.json --top-k 3
```

脚本只依赖标准库与 `rag.text` / `rag.cards`，不联网、不写仓库；输出固定在
`cache/knowledge/audit/` 与 `cache/knowledge/selftest/`。
