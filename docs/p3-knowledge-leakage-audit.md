# P3 知识库泄漏审计报告

## 1. 结论摘要

| 维度 | 结果 | 判定 |
|---|---|---|
| `idx` 交集 | 0（知识库 7,574 个唯一 idx，测试集 300） | 无交集 |
| `commit` 交集 | 0（知识库 3,534 个唯一提交，测试集 149） | 无交集 |
| CVE 编号直接比对 | 测试集无 `cve` 字段 | **无法直接比对** |
| CVE 文本提及 | 测试函数中出现 2 个 CVE，其中 1 个（CVE-2017-5226）在知识库中存在 | 需人工确认 |
| 函数规范化哈希全等 | 0（知识库 7,490 个唯一哈希，测试集 298） | 无交集 |
| 函数片段近似（8-gram 包含度 ≥0.8） | **25 对**，最高 0.9899 | **发现内容级泄漏，需处置** |
| 函数片段近似（0.5~0.8） | 15 对 | 需人工确认 |

一句话结论：**索引层面的 idx / commit / 哈希都干净，但函数内容层面存在 25 对高相似记录**，涉及 25 条测试样本（占 150 对的 16.7%）和 14 条知识记录。已默认把这 14 条知识记录从检索索引中剔除，避免 Agent 检索到与测试样本几乎相同的函数及修复说明。

## 2. 审计口径

1. **idx**：直接比较两边的 `idx` 整数值。
2. **commit**：从 `commit_url` 中提取 `/commit/<hash>`；知识库若没有 URL，则退回 `commit_id`。测试集只有 `commit_url`。
3. **CVE**：`test.jsonl` 没有 `cve` 字段，无法按编号直接比对。替代做法是扫描测试函数文本中的 `CVE-\d{4}-\d{4,7}`，再与知识库的 `cve` 比较。
4. **规范化哈希**：去掉注释与所有非字母数字字符、转小写后取 SHA-1，比较是否全等。
5. **近似片段**：同样规范化后取 8 字符滑窗，按“交集 / 较短一方片段数”计算包含度；单条最多取前 4,000 个字符，避免超长函数拖慢审计。包含度 ≥0.8 视为高相似，0.5~0.8 列入人工复查。

限制：包含度采用较“宽松”的短边分母，小函数被大函数完整包含时会得到高分，因此报告同时给出样例供人工判断；截断 4,000 字符也会让超长函数的尾部差异不被计入。

## 3. 无交集的维度

- **idx**：0 交集。知识库 7,574 个唯一 idx（原始 7,578 行，有 4 个重复 idx），测试集 300 个。
- **commit**：0 交集。知识库 3,534 个唯一提交，测试集 149 个（150 对中有两版共享同一提交 URL 的情况）。
- **规范化哈希**：0 交集。两边各 7,490 / 298 个唯一哈希，没有逐字相同的函数。

这三项说明：测试样本没有以“同一条记录”的形式混进知识库。

## 4. 需要人工确认的维度

### 4.1 CVE 编号

- 测试集没有 `cve` 字段，无法直接做编号交集，只能扫描函数文本。
- 测试函数里出现 `CVE-2015-2141` 与 `CVE-2017-5226`；后者在知识库中有对应记录（项目 `bubblewrap`，2 条）。
- 命中位置是测试样本注释里对漏洞编号的引用，函数内容与知识库记录并非同一函数（未进入 ≥0.8 列表）。结论是“编号相关但非函数级重复”，是否视为泄漏取决于评测口径，建议人工确认。

## 5. 处置

1. `rag/build_index.py` 默认读取本报告，把 `high_similarity_knowledge_idxs` 中的 14 条知识记录从索引中剔除：
   `3124, 9422, 10721, 160967, 195248, 195681, 196630, 197265, 198330, 223203, 254048, 411984, 458139, 484093`。
2. 卡片总数从 7,574 降到 7,560，`manifest.json` 的 `leakage_filter` 字段记录阈值、剔除数量与 idx。
3. 如需保留全部知识做研究，可用 `python -m rag.build_index --include-leaky`，但不建议在评测环境使用。
4. 0.5~0.8 的 15 对未剔除，建议后续人工抽查后再决定是否扩大剔除范围。
