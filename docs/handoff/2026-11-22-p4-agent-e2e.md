- 分支：`feat/p4-agent-e2e`
- 基线：`main` @ `43d7bea`（P2 已通过 PR #2 合并）
- 日期：2026-11-22
- 范围：单条样本从读取快照到输出报告的最小闭环；不做批量、不做 RAG、不做前端

## 1. 范围与结论

本里程碑验证的是“一条样本能完整跑通”，不是各模块单独可用：

```
样本(test.jsonl) -> 快照元数据 -> 只读工具 -> 自主 Agent 循环 -> TraceEvent -> result.jsonl + report.json
```

结论：

- 链路已跑通。用 `idx=194989`（ImageMagick6，target=1）实跑，自动补齐配对样本 `idx=218785`，两版各 4 个 LLM 步、3 次工具调用后收尾。
- 当前环境没有可用的模型 API key，实跑使用确定性 stub provider；输出已标注 `is_stub=true`，**不代表真实检测能力**。
- 最终配对结论为 `P-B`（两版都报 0，未检出），属于 stub 的预期结果，不应当作检测效果。

## 2. 做了什么

### 2.1 只读仓库工具（`repo_tools/`）

| 工具 | 作用 | 关键限制 |
|---|---|---|
| `find_files` | 按文件名通配符/子串查找 | 只返回快照内相对路径；跳过 `.git` |
| `grep_content` | 按正则或固定字符串搜索内容 | 跳过二进制、超大文件；限制命中数/扫描文件数 |
| `read_file` | 读取指定文件的行区间 | 只能读快照内文本文件；限制文件大小与行数 |

- `SnapshotGuard` 统一做路径守卫：拒绝绝对路径、`..` 越界和符号链接逃逸。
- 三个工具统一返回 `ToolResult`：`ok / tool / arguments / data / error / elapsed_ms`。
- `registry.dispatch` 统一计时与异常封装；`summarize` 生成写入 TraceEvent 的精简摘要。
- 工具本身只做文件 I/O，不发起任何网络请求。

### 2.2 Agent 核心（`backend/`）

- `backend/agent/loop.py`：通用自主循环。
  - 模型决定下一步是调用工具还是收尾；循环不预设工具顺序。
  - 每次工具调用写入 `repo_tool` TraceEvent；每次模型响应写入 `llm_step`。
  - 保护：`FUNCGUARD_AGENT_MAX_STEPS`（默认 8）与 `FUNCGUARD_AGENT_TIMEOUT`（默认 120s）。
  - 超时、达到最大步数、模型返回非法 JSON、provider 报错时，保守判定 `benign`，并写入 `error` 事件。
- 证据门控（`apply_evidence_gate`）：
  - 只有“至少一次成功工具调用 + 至少一条可在快照中复核的 evidence 路径”才保留 `vulnerable`；
  - 否则强制降级为 `benign`，理由中追加门控说明。
- 输出版本化：`result.jsonl` 严格只含 `idx` 与 `prediction`；P-x 分类、理由、工具轨迹写在 `report.json`。
- `backend/providers/`：
  - `openai_compat.py`：OpenAI 兼容 Chat Completions + function calling，支持本机代理；
  - `stub.py`：确定性 stub，按对话中已有工具结果自主决定下一步（find → grep → read → 收尾）；
  - `__init__.py`：无 key 时自动回退 stub，并返回明确的回退原因。
- `backend/services/`：
  - `sample_service.py`：读测试集、找相邻配对、读 `cache/meta/samples/{idx}.json`；
  - `run_service.py`：编排一次或一对样本，写 `result.jsonl / report.json / trace.jsonl`。
- `backend/cli.py`：命令行入口，打印 provider、步数、工具轨迹、结论、理由与配对分类。

### 2.3 契约映射

`shared/contracts/result_record.schema.json` 只允许 `idx` 与 `prediction`，因此：

| 内容 | 写入位置 |
|---|---|
| `idx` + `prediction(0/1)` | `result.jsonl` |
| `P-C / P-V / P-B / P-R` | `report.json` 的 `pair.category` |
| 判定理由 | `report.json` 的 `runs[].reason` |
| 工具调用轨迹 | `report.json` 的 `runs[].tool_calls` 与 `trace.jsonl` |
| 运行事件 | `trace.jsonl`（严格按 TraceEvent 契约） |

P-x 按官方相邻配对口径计算：`(漏洞版预测, 修复版预测)` →
`(1,0)=P-C`、`(1,1)=P-V`、`(0,0)=P-B`、`(0,1)=P-R`。

## 3. 怎么验证

以下命令均在仓库根目录执行。运行前需已有快照元数据
`cache/meta/samples/194989.json` 与 `cache/meta/samples/218785.json`（P2 已产出）。

```powershell
# 语法检查
python -m compileall -q backend repo_tools

# 端到端运行（自动补齐相邻配对样本）
python -m backend.cli run --idx 194989 --out cache/runs/p4-e2e-demo

# 只看单条样本
python -m backend.cli run --idx 194989 --single --out cache/runs/p4-single

# 用评测脚本复核 result.jsonl（需要完整数据集与全部预测）
python -m bench.score --result cache/runs/p4-e2e-demo/result.jsonl
```

模型相关环境变量（全部可选；key 只从环境读，不写入仓库）：

| 变量 | 默认 | 作用 |

| `FUNCGUARD_LLM_PROVIDER` | `auto` | `auto` / `openai` / `stub` |

### 4.2 产物与契约

`result.jsonl`（严格两字段）：

```
{"idx": 194989, "prediction": 0}
{"idx": 218785, "prediction": 0}
```

`trace.jsonl`：共 20 条事件，字段集合为
`run_id / seq / type / status / timestamp / name / duration_ms / payload`；
每个 run 包含 1 条 `run_start`、4 条 `llm_step`、3 条 `repo_tool`、
1 条 `decision`、1 条 `run_end`。

`report.json`：包含 provider（含 `is_stub` 与回退原因）、配对分类、
每个 run 的步数、工具轨迹、理由、证据门控与契约映射。

### 4.3 证据门控与保护验证

用四个测试 provider 直接驱动循环（不写入仓库）：

```
fake-no-evidence  verdict=benign   gate={'applied': True, 'note': '没有任何成功的仓库工具调用'} steps=1
fake-evidence     verdict=benign   gate={'applied': True, 'note': '没有任何成功的仓库工具调用'} steps=1
fake-with-tool    verdict=vulnerable gate={'applied': False, 'note': '证据可在快照中复核：1 条'}
fake-loop         verdict=benign   gate={'applied': True, 'note': '达到最大步数 2 仍未收尾...'} hit_max_steps=True
```

结论：无证据的 `vulnerable` 会被降级；只有在成功调用工具且 evidence
路径可在快照中验证时才保留 `vulnerable`；死循环会触发最大步数保护。

## 5. 没做什么 / 已知限制

- 没有真实模型 key，未验证 OpenAI 兼容 provider 的实际检测质量；本次所有结论均来自 stub。
- 只验证了 1 对样本（2 条），没有批量跑 300 条，也没有接 `bench.score` 做全量评级。
- 未实现 RAG / knowledge_search；TraceEvent 的 `knowledge_search` 类型暂未使用。
- 未做 Tree-sitter 等结构化分析，工具只做文本级定位与读取。
- 未实现工具级硬超时：靠单样本总超时、最大步数、扫描文件数与文件大小上限共同约束。
- 未提供 HTTP API / SSE / 前端页面；当前只有 CLI。
- 单个样本快照缺失时整次运行会报错退出，尚未做“逐样本失败记录、其余继续”。

## 6. 踩坑与约束

1. **契约只允许两个字段**：`result_record.schema.json` 是
   `additionalProperties: false`，不能把 P-x、理由、轨迹塞进 `result.jsonl`；
   必须写到 `report.json`。
2. **不要让模型看到标签**：用户提示词只给 idx、commit_url、函数文本与快照目录，
   不传 `target`/`version_role`，避免标签泄漏。
3. **stub 不是检测器**：stub 只根据对话状态决定下一步，固定给出 `benign`；
   所有输出必须保留 `is_stub` 标注。
4. **证据门控是硬门槛**：`vulnerable` 必须同时满足“成功工具调用 + 可复核路径”，
   否则降级为 `benign`（对应 P-B），避免误报拉低等级。
5. **路径守卫**：工具只接受快照内相对路径；`SnapshotGuard.resolve` 会拒绝
   `../`、绝对路径与逃逸符号链接。
6. **二进制与大文件**：`grep_content` / `read_file` 通过 NUL 字节嗅探与大小上限跳过，
   避免读图片、压缩包。
7. **不要提交缓存与密钥**：`cache/` 已在 `.gitignore`；key 只从环境变量读取，
   代理默认 `http://127.0.0.1:7897`，不写进仓库配置。
8. **超时与步数是兜底**：循环每步都检查剩余时间；工具本身是同步的，
   大仓库搜索靠 `FUNCGUARD_TOOL_MAX_SCAN_FILES` 限制，必要时调小。
